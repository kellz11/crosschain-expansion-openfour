# ADR-002 — BNB-only current OpenFour integration

Decision (0.2.0): BNB is the sole launch destination; Solana remains backing. Use the current developer/startup layout, solc 0.8.24 and hash-pinned public interfaces. Replace StandardTokenModule with a thin standard initializer plus discoverable bootstrap schema. Reuse StandardVault and SimpleTradeModule through developer-owned OpenFour proxies. Accept authorized CreateDeployer initialization with token binding. Prepare and register the Pancake pair before funding, accept empty pre-created pairs and quote-only donations, and verify direct pair funding/minting.

The fork lifecycle verifies the public testnet implementation behavior; production still requires official registration, signer policy, live bridge validation and independent audit. Registry beacons are upgradeable. A fresh matching price attestation may be impossible after market movement: this version does not implement cancellation/repricing, and inactive inventory can remain locked.

The original ADR below is historical and superseded wherever it differs.

# ADR-001 — Minimum viable OpenFour integration

Status: selected for a reference implementation; production acceptance is conditional on the gates below. Research snapshot: 2026-09-19 (America/Indianapolis).

## Evidence and constraints

OpenFour `0527d529d59c6a3fbc9927ce391ecc97c66e1b01` publishes Developer Guide 0.0.2, Integration Guide 0.0.4, clone interfaces, OpenFourToken and StandardVault. It does **not** publish the standard BondingCurveModule, SimpleTradeModule, BondingPcsV2MigrateModule, production Core/Registry, or underlying migration libraries. The FairLaunch migration sample references `ctx.soldOut` in a struct without that member; compiling all samples unmodified is not possible. We compile the actual interfaces and the reused source dependency closure, without modifying upstream.

Source: https://github.com/four-meme-community/openfour-docs/tree/0527d529d59c6a3fbc9927ce391ecc97c66e1b01

LayerZero devtools snapshot `4973ba8bef7b0fdf7268469abea3ea50dbd4bbd8` includes MintBurnOFTAdapter, the Solana Adapter debit/credit implementation, and distinct pauser/unpauser authorities. No permissioned-depositor feature is assumed.

Source: https://github.com/LayerZero-Labs/devtools/tree/4973ba8bef7b0fdf7268469abea3ea50dbd4bbd8

## Options

| Option | Compatibility / Four.Meme change | Security and audit burden | Bridge / upgrades / UX / future chains |
|---|---|---|---|
| 1. All standard modules, custom bridge only | Standard initial mint violates backing; cannot accept unchanged | Small code but incorrect supply model | Reject; minting on creation is not a bridge credit |
| 2. Custom token; all other standard modules | Override initial mint; requires confirmation of standard curve parameters and migrator behavior | Preferred production target if those checks pass | Separate OFT adapter avoids clone/OApp ownership collisions; asynchronous funding must be supported |
| 3. Custom token + curve, standard Vault/Trade/Migrate | Curve interface is public; standard migration internals unavailable | Small pricing module with explicit reserve bounds; migrator still unverified | Preferred if standard migrator is compatible with zero initial quote and backed remainder handling |
| 4. Custom Token + Vault + Curve/Migrate | Vault replacement unnecessary: real quote accounting is already separate | Reject custom Vault; use custom curve and thin migration fallback only | More modules to review than option 2, but no new custody contract |
| 5. External wrapper | Public create flow clones a token; no existing-token market API is established | Staged wrapper adds conversion and custody surface | Reject as default; requires Core lifecycle changes or redundant tokens |

## Decision

Model B: an OpenFourToken subclass with its initial mint suppressed, plus a per-launch LayerZero MintBurnOFTAdapter. Only the adapter can mint/burn. StandardTokenModule initializes the subclass unchanged. StandardVault is reused unchanged. SimpleTradeModule is requested for production; a clearly labelled mock is used locally because its source is not public. No CustomData or CurveReceipt.

The executable reference uses a custom curve and thin V2 migration module because the public repository is insufficient to prove the standard equivalents safe for these parameters. These are **fallbacks**, not a claim that standard modules cannot support expansion. Four.Meme can remove either after verifying the precise requirements in OPENFOUR_INTEGRATION.md. V2 is explicitly listed in the official guide and has simple full-range reserve accounting. We do not claim it is Four.Meme's recommended current default; that is an integration decision for them. V4/Infinity support would require a separate reviewed position adapter, not a renamed V2 router.

## Bootstrap and activation

Create the OpenFour token with zero minted supply and fixed sale configuration. Deploy its dedicated adapter during initialization. Send the exact inventory from the canonical Solana Adapter into the standard vault. The Solana store remains paused except within one atomic unpause/send/pause transaction. Before public mode, the destination only accepts the exact inventory, bound vault, authenticated source signer in OFT compose bytes, and unique bootstrap identifier. All later inbound messages fail until migration completes; outbound sends also fail. The signed source-market attestation is consumed in an explicit activation transaction after funding. Trading quotes remain non-executable until activation. Thus price expiry cannot strand a delivered bootstrap: obtain a fresh attestation for the same fixed curve price, or leave the launch inactive.

The adapter learns graduation from both the immutable migration module's success flag and the token's terminal `Migrated` phase. It cannot be opened by an owner switch. Source unpause is a separate operator transaction after finality; the source operator can delay service, but cannot bypass the destination gate.

## Assumptions requiring acceptance

1. Core accepts zero `totalSupply` at creation while sale inventory is funded asynchronously; Core can expose created-but-unfunded launches without selling them.
2. Core calls the registered token implementation through the standard token module atomically, and enforces the registered preset/validator.
3. Core uses quotes/fees/transfers and rollback semantics consistent with the public lifecycle. Anti-sniper is disabled for this version.
4. Core's migration transfers and final phase changes occur atomically; failed migration can be retried.
5. Production migration/LP policy is supplied and audited. No public Core deployment is substituted with a mock address.

If (1) fails, stop integration and negotiate a narrow delayed-activation extension; do not silently pre-mint tokens or assume Model C.
